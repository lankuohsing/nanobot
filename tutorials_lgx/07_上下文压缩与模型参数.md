# 07：上下文压缩与模型参数

上下文压缩会用摘要替换后续请求中的历史原文，已保存的聊天记录仍保留。模型生成参数与上下文预算配置在当前选中的模型预设里；闲置压缩设置在 `agents.defaults`。本文依据当前源码与 2026-11-18 的只读配置检查，版本基准见 [README](./README.md)。

## 1. 什么时候压缩

| 触发方式 | 当前行为 |
| --- | --- |
| 输入预算压力 | 每次模型请求前检查，包含一个回合内的后续工具循环；测量或估算的请求上下文达到输入预算时，尝试压缩已接收的历史 |
| 会话闲置 | 当前配置为 15 分钟，运行中的 AgentLoop 每 60 秒检查一次；会话有尚未归档的消息且没有活跃回合时，安排摘要任务 |
| 手动压缩 | 在目标对话发送 `/compact`，不必等待时间或 token 阈值 |

当前公司接口使用 Chat Completions，普通请求的本地输入预算为：

```text
输入预算 = contextWindowTokens - maxTokens - 1024
当前配置 = 200000 - 8192 - 1024 = 190784 tokens
```

| 数值 | 对应项 | 含义 |
| --- | --- | --- |
| `200000` | `contextWindowTokens` | 配置给 nanobot 的总上下文容量，为输入与输出共同留空间；应与公司模型真实窗口匹配 |
| `8192` | `maxTokens` | 为这次模型回复预留的最大输出空间，实际回复可以更短 |
| `1024` | 源码中的 `CONTEXT_SAFETY_BUFFER` | 框架固定预留的安全余量 |
| `190784` | 本地输入预算 | 扣除输出预留与安全余量后，本次请求可使用的输入空间 |

nanobot 在发请求前按最大输出预留空间，不等实际回复生成后再计算。因此保持总窗口不变时，增大 `maxTokens` 会减少可用输入预算。

输入预算包含系统提示、Skill、历史/摘要、当前输入、工具定义与工具结果等材料，不只是用户输入的字数。源码优先利用适用的服务端用量，其他情况估算；这是 token 预算，不是字符数，也不是固定聊多少轮后压缩。若配置了更小窗口的回退模型，还会按回退链的最小窗口构建请求。

压缩会将已接收的历史换成摘要，保留本次新增输入；若新增输入等材料仍装不进预算，请求可能失败。闲置和手动压缩会将尚未归档的历史整体摘要化，后续使用摘要与新消息；即使最近的消息也可能不再逐字送给模型。摘要生成会调用模型，可能丢失细节；SQLite 中保存的历史仍可回看，压缩也不改变 session key。Memory 分层与保存位置见 [第 06 章](./06_工作区与会话存储.md)。

Gateway/WebUI 运行时有持续的 AgentLoop，可执行闲置扫描。单次 `agent -m` 自身回复后就退出，不会留一个闲置计时器；同实例的 Gateway 继续运行时仍可扫描这份已保存的 CLI 会话。支持原生压缩的其他 Provider/API 还有服务端压缩路径，具体阈值由对应适配器管理。

## 2. 模型参数在哪里修改

当前学习实例的配置文件是 `tutorials_lgx/.runtime/config.json`，默认选中 `agents.defaults.modelPreset = "company"`。因此应修改已有的 `modelPresets.company` 对象中的参数，保留其 `provider`、`model`、`api` 等字段。

将下面的字段合并到 `modelPresets.company`；这是该对象内的字段片段，不能替换整份配置或整个预设：

```json
{
  "temperature": 0.1,
  "maxTokens": 8192,
  "contextWindowTokens": 200000
}
```

| 字段 | 含义 | 当前配置值 |
| --- | --- | --- |
| `temperature` | 采样温度；通常越低，随机性越小 | `0.1` |
| `maxTokens` | 单次模型请求的最大输出 tokens；不是整个 Agent 回合的总额度 | `8192` |
| `contextWindowTokens` | nanobot 判断上下文容量、预留输出空间与触发压缩的依据 | `200000` |
| `reasoningEffort` | 可选思考强度；支持情况取决于模型与服务 | 按服务支持设置 |

`contextWindowTokens` 是本地容量配置，不作为这个 Chat Completions 请求的同名字段发送；它不会扩大公司服务的真实窗口。表中 token 数沿用当前配置，尚未验证公司的最大输入/输出限制。应按公司 API 文档填写实际支持的上下文容量与最大输出，通常保持 `contextWindowTokens > maxTokens + 1024`，为输入留出空间。推理模型的输出限制是否计入思考 tokens，以服务协议为准。

当前 OpenAI 兼容适配器将 `maxTokens` 转为 `max_tokens`，部分模型使用 `max_completion_tokens`；温度也会按适配器支持情况发送。需要 `top_p` 或其他服务扩展字段时，可在同一预设的 `extraBody` 中添加服务明确支持的字段，通用温度与输出预算仍使用上表字段。

已配置命名预设时，直接修改 `agents.defaults.temperature` 等字段会改变隐式 `default` 预设，当前 `company` 预设继续使用自己的参数。已有会话可以保存另一份预设选择，用 `/model company` 切换；本次检查中 CLI 与网页会话均未保存覆盖选择，跟随默认的 `company`。

也可在 WebUI 的 **设置 → 模型 → company 预设 → 高级选项** 修改温度、最大输出与上下文窗口。手动编辑文件后重启对应 Gateway，以确保重新加载；单次 CLI 请求在下一次启动时重新读取配置。WebUI 修改按界面保存及重启提示处理。

## 3. 闲置压缩参数在哪里修改

在现有 `agents.defaults` 对象中合并下面两个字段，保留模型预设、工作区及其他设置：

```json
{
  "idleCompactAfterMinutes": 15,
  "idleCompactCheckIntervalSeconds": 60
}
```

`idleCompactAfterMinutes` 是会话闲置阈值，设为 `0` 关闭闲置压缩；输入预算压力与手动 `/compact` 仍然生效。`idleCompactCheckIntervalSeconds` 是扫描间隔，设为 `0` 表示每次空闲 tick 都扫描，约 1 秒一次。达到时间阈值后，还需等待一次扫描并完成模型摘要，因此不是精确在第 15 分钟完成。

每份 session 分别按最后更新时间 `updated_at` 计算闲置，通常对应最近一轮问答或状态更新。网页保持打开也可以闲置；Gateway 需要继续运行，且该会话没有正在执行的回合。“有待压缩历史”指上次归档之后还有消息，例如新完成的一轮问答；空会话或已归档且没有新消息的会话会跳过。

例如，Gateway 持续运行时：

| 时间 | 发生什么 |
| --- | --- |
| `10:00` | 一轮问答完成，之后没有新的会话活动 |
| `10:15` 以后的一次扫描 | 发现已闲置至少 15 分钟且有待压缩消息，安排模型生成摘要 |
| 摘要完成后再次提问 | 模型使用摘要和新消息继续回答，完整聊天记录仍保存在数据库中 |

每 60 秒检查一次，并不表示每 60 秒都生成摘要；检查闲置条件不需要摘要模型请求，符合条件并开始压缩时才调用模型。若 `10:10` 又完成一轮问答，闲置计时随会话更新重新开始，下一次要到约 `10:25` 之后才符合时间条件。一轮短问答也可能满足闲置压缩条件，它不要求先聊满很多轮。

WebUI 入口为 **设置 → 系统 → 会话**，修改自动压缩开关和闲置时间后重启 Gateway；扫描间隔直接在配置文件修改。压缩与 Dream 是不同步骤：压缩产生会话摘要及 `memory/history.jsonl` 材料，Dream 再整理长期记忆。

### 为什么在闲置时压缩

核心目的是减少以后继续对话时携带的输入 tokens。Chat Completions 的后续请求通常会携带历史；将历史提炼成短摘要，可以减少上下文占用，并可能降低后续输入成本与处理时间。闲置意味着一段交互暂时告一段落，适合在后台整理；若等输入预算耗尽才压缩，则当前回合需要先等待摘要完成。压缩产出的归档摘要也可供 Dream 提炼长期记忆。

15 分钟和 60 秒是框架的默认策略值，不是模型协议要求，也不表示模型在 15 分钟后忘记对话。可以将 15 分钟理解为判断“暂时不再继续聊”的时间阈值；一分钟一次的扫描在检查开销与触发及时性之间取舍。

这项策略有成本与信息保真度的取舍：摘要生成本身需要模型请求，而且摘要可能遗漏原始细节。输入 tokens 减少也不保证净费用必然下降，需要结合后续请求次数及服务端 prompt cache 的计费和保留时间评估；重写历史前缀可能影响缓存命中。官方文档建议缓存保留更久时延长闲置阈值，并没有承诺公司服务的缓存恰好在 15 分钟失效。

源码学习和对照实验经常会暂停较长时间。为了观察同一份原始上下文，可暂将 `idleCompactAfterMinutes` 设为 `0`，保留输入预算压力触发与手动 `/compact`；这只是实验建议，本轮没有修改运行配置。金融任务中需逐字核对的数字、日期、引用等，应仍能从原始会话或业务数据源取回，摘要负责提供继续任务的背景。

## 4. 各种压缩结果放在哪里

输入预算压力、闲置和手动 `/compact` 是不同的触发原因，正常持久化会话使用相同的保存位置。压缩生成的内容有两个主要用途：继续当前会话，以及给后续长期记忆整理提供归档材料。

| 内容 | 当前学习实例中的位置 | 怎么使用 |
| --- | --- | --- |
| 最新会话摘要 | `.runtime/sessions/<workspace-id>/sessions.sqlite3` 的 `sessions.metadata` JSON 中，字段为 `_last_summary.text` | 下次请求与新消息一起进入模型上下文；每份 session 各有自己的最新摘要，后续压缩会更新它 |
| 归档摘要 | `.runtime/workspace/memory/history.jsonl` | 有内容的归档通常追加为 JSON 行，包含 `cursor`、`timestamp`、`content` 和 `session_key`，供 Dream 整理；已处理记录可能按保留策略清理 |
| 提炼后的长期资料 | `.runtime/workspace/memory/MEMORY.md`、`.runtime/workspace/USER.md`、`.runtime/workspace/SOUL.md` | Dream 后续按需要更新；普通压缩不会直接把所有摘要写进这些文件 |

SQLite 中还会记录用于回放的隐藏检查点及摘要覆盖边界；已有聊天历史仍保存在数据库中。数据库的最新会话摘要和 JSONL 的归档用途不同，截断、降级归档等处理也可能让内容不完全一致。支持原生压缩的 Provider/API 还可能维护协议续接状态；生成可移植会话摘要时，继续使用上述保存位置。

特别注意 `(nothing)`：归档提示要求在没有符合条件的事实或活跃任务状态时返回这个标记。源码仍可将它保存为当前 session 的摘要检查点，但不会把它追加到 `history.jsonl`。因此，JSONL 为空不能单独证明会话尚未压缩。

2026-11-19 的只读检查确认：`lgx:company-first` 和当前网页会话均已有 `_last_summary.text = "(nothing)"` 及归档边界；`history.jsonl` 仍为 0 字节，`SOUL.md`、`USER.md`、`MEMORY.md` 仍是默认模板。这说明本地已有压缩检查点，摘要生成器选择了“无可保留信息”，没有产出归档条目；本轮没有重新触发压缩。

先按 [第 06 章](./06_工作区与会话存储.md#2-刚才的问答存在哪里) 设置 `LGX_SESSION_DB`，再用下面的只读命令查看：

```bash
# 查看每份 session 当前保存的续聊摘要
sqlite3 -readonly -line "$LGX_SESSION_DB" \
  "SELECT key, json_extract(metadata, '$._last_summary.text') AS summary,
          last_archived FROM sessions;"

# 查看最近的归档记录；文件为空时没有输出
tail -n 5 "$LGX_NANOBOT_HOME/workspace/memory/history.jsonl"
```

这些命令查看本地真实内容；复制到共享笔记前只保留必要的脱敏信息。
