# 02：从当前源码收到第一条回复

学习目标：安装当前源码、初始化独立实例、配置模型并收到第一条回复，再观察 WebUI 与运行文件。版本基准见 [README](./README.md)；个人学习进度放在本章末尾，教程步骤供新同事独立执行。

## 1. 准备源码环境

前提：已取得项目源码、Python 3.11+，可访问依赖仓库；模型调用阶段还需要公司提供的接口与凭据。以下命令用于 macOS/Linux，默认从自己的 nanobot 仓库根目录执行。先选择并激活一个环境，后续统一使用 `python -m ...`，避免把包安装到另一个 Python 中。

新同事可以新建独立环境，避免与其他项目的依赖互相影响。下面要求本机已安装 `python3.12`；其他 Python 3.11+ 解释器也可以替换它。

```bash
python3.12 -m venv .venv
source .venv/bin/activate
```

如果复用已存在的 Conda 环境，则跳过上面两行，执行下面的激活命令。`py312` 是当前作者的环境名，新同事应替换为自己的环境名；需要新建 Conda 环境时见 [依赖排障](./04_依赖检查与排障.md#4-处理冲突的两种方式)。

```bash
conda activate py312
```

激活后安装源码。已有环境不需要先逐个检查和安装 nanobot 的依赖，`pip install -e .` 会根据 [pyproject.toml](../pyproject.toml) 自动解析并安装所需包。

```bash
git branch --show-current
git rev-parse --short HEAD
python --version
python -c 'import sys; print(sys.executable)'

python -m pip install -e .
python -m pip check
python -m pip show nanobot-ai
python -m nanobot --version

python -c 'import sys, nanobot; print(sys.executable); print(nanobot.__file__)'
```

`-e` 表示可编辑安装：解释器使用当前仓库的源码。后续修改 Python 源码通常不需要重新安装，但已运行的进程需要重启；改动依赖或安装元数据后需重新安装。`nanobot-ai` 是安装包名，`nanobot` 是导入模块和命令入口名。

通过标准：Python 路径属于所选环境，`pip show` 的 `Editable project location` 指向当前仓库，导入路径指向该仓库的 `nanobot/__init__.py`，版本与当前 `pyproject.toml` 一致，`pip check` 输出 `No broken requirements found.`。在仓库里成功导入也可能来自当前目录，因此导入路径应结合可编辑安装信息一起检查。依赖冲突及原始安装输出的解释见 [第 04 章](./04_依赖检查与排障.md)。

## 2. 初始化学习实例并配置模型

使用单独的实例 home 保存学习状态。`--home` 是全局参数，放在子命令前；后续运行或管理这个学习实例时使用同一个 home。该目录已通过本目录 `.gitignore` 排除。首次执行下面的初始化命令；已有这个实例时跳过 `onboard`。

```bash
# 从仓库根目录执行；每个新终端重新设置这个变量
export LGX_NANOBOT_HOME="$PWD/tutorials_lgx/.runtime"
python -m nanobot --home "$LGX_NANOBOT_HOME" onboard
```

`LGX_NANOBOT_HOME` 是我们自定义的 shell 变量，nanobot 不会自动读取这个名字。`$PWD` 是执行命令时的当前目录，因此路径为 `<你的仓库>/tutorials_lgx/.runtime`。`export` 使后续启动的子进程也能读取变量，但本身不会创建目录、初始化 Agent 或切换工作目录，也不影响 Python 虚拟环境。

真正选择实例目录的是后续的 `--home "$LGX_NANOBOT_HOME"`；变量只是避免重复输入路径。只设置变量却省略 `--home` 时，nanobot 仍使用默认 home `~/.nanobot`。新终端需重新设置变量；已运行的进程不会获得后续 `export` 的值。

并非所有命令都需要 `--home`：针对本学习实例的 `onboard`、`status`、`agent`、`webui`、`gateway` 统一带它，确保选择 `.runtime/`；查看 `--help`、`--version`，以及 `python -m pip install`、`python -m pip check` 等环境操作不需要它。`--home` 选择 nanobot 实例，激活虚拟环境选择 Python 解释器，两者分别控制不同的事情。显式 `--config` 可选择配置及其运行数据目录，但并不等价于切换所有 home 路径，因此本教程仍统一使用 `--home`。

`onboard` 首次生成默认配置，创建工作区，并补齐 `AGENTS.md`、`SOUL.md`、`USER.md`、`HEARTBEAT.md`、记忆文件等初始模板及相关默认配置。已有实例会按提示保留并补齐配置，或由用户选择重置；普通初始化不启动聊天或 Gateway，也不调用模型。实现入口：[onboard](../nanobot/cli/commands.py)、[工作区模板同步](../nanobot/utils/helpers.py)。

预期会看到创建文件的提示，以及 `✓ nanobot is ready. Run: nanobot webui`。它说明初始化步骤完成，模型配置与调用验证还在后续；通用提示省略了自定义 home，后续仍应带同一个 `--home`。本教程接着按 [第 03 章](./03_公司模型接口配置.md) 手动配置公司接口；也可使用可选的 `onboard --wizard` 向导或 WebUI `Settings → Models`。

学习配置位于 `.runtime/config.json`，新实例的 Agent 工作区默认为 `.runtime/workspace/`。已有配置中的 `agents.defaults.workspace` 优先于这个默认值，`--workspace` 可以覆盖工作区；显式 `--config` 会改变配置路径及运行数据所在目录。`--home` 不会搬迁已有文件或重写已保存的工作区路径。重复初始化已有配置时注意向导/命令的提示，保留已配置值。

home 是实例的配置与运行状态根目录，Agent 工作区是它默认包含的 `workspace/` 子目录，保存身份、长期记忆、技能及工作产物。项目工作区则是某条会话实际处理项目文件的目录，决定项目 `AGENTS.md`、相对文件路径与 shell 默认工作目录。选择其他项目不会迁移 Agent 的身份、记忆和技能，也不会创建独立实例。

本章单次 `agent -m ...` 使用配置的 Agent 工作区；当前交互式 TUI 初始项目目录为启动时的当前目录，WebUI 也可另选项目。工作区是实际文件目录及其运行上下文，不是模型的 token 上下文窗口，也不自动构成操作系统沙箱；边界与配置优先级见 [Concepts](../docs/concepts.md#agent-workspace-and-project-workspace) 和 [Multiple Instances](../docs/multiple-instances.md#path-resolution)。

提交的配置示例只保存占位符；本地配置可直接填写实际值，也可使用 `${COMPANY_LLM_API_KEY}` 这样的环境变量引用，并在启动进程的环境中提供该变量。`${VAR}` 是 nanobot 配置解析语法，变量缺失会报错，不支持 shell 的默认值写法。具体字段见 [Configuration](../docs/configuration.md#environment-variables-for-secrets)。

## 3. 检查本地配置，再发起请求

先完成 [公司 API 配置](./03_公司模型接口配置.md#2-手动填写公司-api-配置)，再执行下列命令；使用其他 Provider 时也需先配置有效模型。

```bash
# status 检查本地配置和模型就绪状态，不发送模型请求
python -m nanobot --home "$LGX_NANOBOT_HOME" status

# 该命令会调用已配置模型；固定 session 便于后续查看历史
python -m nanobot --home "$LGX_NANOBOT_HOME" agent \
  --session lgx:first-run -m "用一句中文说明你的作用。"
```

完成标准：status 指向学习实例的配置和工作区，显示预期模型以及 `Agent: ✓ provider/model configuration is ready`；第二条命令收到正常助手回复。status 不验证网络、凭据或配额；实际回复才验证本次模型请求成功。普通 Agent 请求已携带启用的工具定义，因此接口需要接受相应字段；实际工具调用与结果回传仍需单独实验，要求见 [第 03 章](./03_公司模型接口配置.md#4-检查配置与发起第一条请求)。

## 4. 体验 WebUI，观察状态归属

```bash
# 使用独立端口，便于与已有默认实例同时运行
python -m nanobot --home "$LGX_NANOBOT_HOME" webui \
  --yes --port 8766 --gateway-port 18792
```

`--yes` 自动应用本地 WebUI 的默认设置，省去首次配置确认。`--port 8766` 设置 WebUI 页面及 HTTP/WebSocket 通信端口，浏览器入口为 [http://127.0.0.1:8766](http://127.0.0.1:8766)；`--gateway-port 18792` 设置网关健康检查端口，健康端点为 [http://127.0.0.1:18792/health](http://127.0.0.1:18792/health)。两个端口都由 Python Gateway 提供。健康响应检查进程/WebSocket 就绪情况，不验证模型连接。`--gateway-port` 覆盖本次启动的健康端口，不写回配置中的 `gateway.port`。

macOS 启动后会出现名为 nanobot 的猫形 Dock 图标，它是打开 WebUI 的辅助入口。当前实现每次点击都通过系统打开浏览器 URL，因此浏览器可能新增标签页；这些页面连接同一个 Gateway，共享 Agent 工作区与会话数据库，对话历史取决于各页面选择的 session。图标助手本身不执行 Agent 回合、不保存用户数据，也不持有 Gateway 生命周期。下次启动时加 `--no-dock` 可隐藏图标；当前图标应用的顶部菜单也提供 `Hide Dock Icon`，只退出图标助手。实现见 [Dock 入口](../nanobot/cli/dock.py)、[macOS 点击与菜单](../nanobot/cli/_macos_dock.py)。

构建时的 `Some chunks are larger than 500 kB` 是资源体积警告，后续出现 `built` 表示构建成功；`Cannot open this WebUI: the address is already in use` 则表示启动端口冲突。用第 05 章的 `lsof` 命令查看监听进程；端口属于其他应用时，选择空闲端口并修改相应启动参数。当前本机原先使用的 `18791` 被 Node 进程占用，因此教程改用检查时空闲的 `18792`；端口是否空闲仍以每次启动时为准。

源码 WebUI/TUI 会按需使用 Bun 并构建/运行匹配当前检出的客户端，首次启动可能下载资源。完成标准：页面可打开，选择同一模型后收到回复；完成体验后用启动终端的 `Ctrl+C` 结束前台运行。WebUI/TUI 与 Gateway 的受支持组合使用相同版本，远程 Gateway 也遵循这一点。

在 WebUI 新建一条对话，使用相同模型发送一条消息。CLI 的 `lgx:first-run` 与 WebUI 新对话有不同的会话历史，但共享这个实例的 Agent 工作区与长期记忆。观察以下文件即可，不必手动编辑数据库：

| 路径 | 应观察到什么 |
| --- | --- |
| `.runtime/config.json` | Provider、模型与工作区设置；启动参数可覆盖配置端口 |
| `.runtime/workspace/` | `AGENTS.md`、`SOUL.md`、`USER.md` 等工作区资料 |
| `.runtime/sessions/<workspace-id>/sessions.sqlite3` | 会话持久化；普通聊天历史在 SQLite 中 |
| `.runtime/workspace/memory/` | `MEMORY.md` 长期资料与 `history.jsonl` 归档日志；一条回复不保证形成新记忆 |
| `.runtime/workspace/skills/`、`.runtime/workspace/cron/` | 自定义技能与定时任务；按需创建 |
| `.runtime/media/`、`.runtime/logs/`、`.runtime/webui/` | 按功能产生的媒体、日志和 WebUI 状态 |
| `.runtime/run/`、`.runtime/cache/` | 按功能产生的 Gateway 管理状态与缓存 |
| `.runtime/history/cli_history` | 交互式 CLI 输入历史；按需创建 |

上表对应使用同一 `--home`、默认工作区且没有另指定 `--config` 的学习实例；目录会随实际启用功能逐步产生。环境变量中的 API Key 不会因为设置 home 自动保存为文件；配置中可只保存 `${COMPANY_LLM_API_KEY}` 这样的引用。Agent 在另选项目或工具指定的其他允许路径写出的产物，则可能位于 `.runtime/` 之外。

工作区中各个文件的具体作用、只读查看问答的命令，以及 CLI 会话为何不出现在网页侧栏，见 [第 06 章](./06_工作区与会话存储.md)。

Git 已通过 [本目录的 .gitignore](./.gitignore) 中的 `/.runtime/` 忽略整个实验目录及子文件；规则相对于这个 `.gitignore` 所在目录。可从仓库根目录执行 `git check-ignore -v tutorials_lgx/.runtime/config.json` 查看生效规则；不需要在根 `.gitignore` 重复添加。
