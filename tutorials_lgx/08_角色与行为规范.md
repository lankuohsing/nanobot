# 08：角色与行为规范

角色主要写在 Agent 工作区的 `SOUL.md`，项目任务规范写在当前项目的 `AGENTS.md`，用户资料与稳定偏好写在 Agent 工作区的 `USER.md`。当前实现会把这些内容拼接进 system prompt，影响模型的回答、任务规划和工具选择；必须强制执行的限制还需落实到工具权限与代码中。本文依据当前检出源码，版本基准见 [README](./README.md)。

## 1. 应该修改哪些文件

当前学习实例的 Agent 工作区是 `tutorials_lgx/.runtime/workspace/`，默认项目也使用这个目录。下表中的 Agent 工作区文件会被同实例的多份会话共享，新建 session 不会创建另一套角色与规范。

定时任务每次独立开始的场景，保留稳定角色和项目规则，并单独控制历史与动态记忆的加载，见 [第 09 章](./09_独立定时任务与状态隔离.md)。

| 文件 | 建议写什么 | 从哪里读取 |
| --- | --- | --- |
| `SOUL.md` | Agent 身份、职责、表达风格，以及希望跨项目保持的交互原则 | 始终从配置的 Agent 工作区读取 |
| `AGENTS.md` | 当前项目的工作步骤、数据口径、工具使用约定、输出要求 | 从当前会话的有效项目目录读取 |
| `USER.md` | 用户的技术背景、语言、时区、稳定偏好 | 始终从 Agent 工作区读取 |
| `memory/MEMORY.md` | 已确认的长期事实、工作背景与决策 | 默认持久化会话从 Agent 工作区读取；不是主要的角色配置入口 |
| `skills/<技能名>/SKILL.md` | 某类任务的具体方法，例如财报指标分析流程 | 自定义技能从 Agent 工作区发现；符合条件的 `always` 技能注入完整内容，其他技能通常先提供摘要、再按需读取 |

2026-11-19 的只读配置与会话检查确认，当前 CLI 与网页会话均使用上述默认项目。因此现在可直接用本地编辑器修改 `.runtime/workspace/SOUL.md`、`.runtime/workspace/AGENTS.md` 和 `.runtime/workspace/USER.md`。

WebUI 为新会话另选项目时，读取的是所选目录里的 `AGENTS.md`；该目录没有此文件时，不会回退到 Agent 工作区的 `AGENTS.md`。`SOUL.md`、`USER.md` 和长期记忆仍来自原 Agent 工作区，所选项目中的同名身份文件会被忽略。nanobot 不沿父目录逐级继承 `AGENTS.md`。三个目录层次见 [第 06 章](./06_工作区与会话存储.md)。

仓库根目录和 `tutorials_lgx/` 内的 `AGENTS.md` 目前指导开发与学习协作；只有当对应目录被选为 nanobot 的有效项目时，该目录的文件才会作为 nanobot 的项目指令读取。定制当前实例通常无需改 `nanobot/templates/` 或 `ContextBuilder`，前者是随包模板与框架提示，后者是组装机制。

## 2. 怎样进入模型请求并影响执行

`ContextBuilder.build_system_prompt()` 读取文件并拼接字符串；`build_transcript()` 将结果放在第一条 `role = "system"` 消息里。对当前公司的 Chat Completions 接口，请求结构可以简化为：

```text
messages = [
  system: 框架运行说明
          + 项目 AGENTS.md + Agent SOUL.md + USER.md
          + 框架工具使用规范与项目说明
          + 有效长期记忆 + 技能内容/摘要 + 有效会话摘要,
  历史消息（assistant、user、tool 等）,
  user: 本次输入与运行上下文
]
tools = 当前注册工具的描述和参数定义
```

上述文件作为文本段落进入同一个 system 消息，不会变成几个独立 Agent，也没有 `AGENTS.md > SOUL.md > USER.md` 这样的程序化优先级。文件间应避免互相矛盾；工具定义通过请求的 `tools` 字段提供，写一句“使用某工具”不会自动安装或注册该工具。

模型结合这些指令、历史和本次输入决定如何回答、如何分解任务以及是否提出工具调用。`AgentRunner` 执行模型与工具循环，工具及 Python 运行时再检查权限、参数等条件，返回结果供模型继续处理。因此“金额必须用工具计算”会引导模型选择工具；金额口径校验、计算公式和数值正确性仍应由工具实现。

未修改的默认 `AGENTS.md`、`USER.md` 和 `MEMORY.md` 会被跳过，避免把空白模板当成有效指令。修改后的非空内容会进入相应上下文；`SOUL.md` 默认也会加载。`memory/history.jsonl` 不会整份直接拼进普通对话的 system prompt，它主要供归档检索与 Dream 使用。

## 3. 金融分析场景的最小示例

下面只是可手动填写的示例，不是已经生效的配置。按自己的职责和业务口径调整，尽量用可观察的动作描述规则。

在 `SOUL.md` 中定义角色与风格：

```markdown
# 角色与职责

你是一名金融数据分析助理，帮助用户核对公开财务数据、计算指标并解释结果。

- 默认用中文，先给结论，再给证据和计算依据。
- 明确区分已知事实、计算结果与假设；数据不足时说明缺少什么。
- 表述简洁，保留会影响结论的条件和不确定性。
```

在有效项目的 `AGENTS.md` 中定义具体工作流程：

```markdown
# 本项目的分析规范

1. 先确认分析对象、数据时点、币种、单位与指标口径。
2. 涉及金额、比例、增长率等计算时，使用确定性的工具或代码，并列出公式。
3. 引用数据时注明来源和时间；缺失数据不编造，不用未说明的假设补齐。
4. 最终回答包含结论、关键数据、计算依据，以及会影响结论的限制。
5. 本项目只做数据查询与分析，不执行交易。
```

用户的背景与偏好可写在 `USER.md`，例如“用户熟悉 Python、大模型和 Agent，希望解释包含源码入口”。这些是个性化背景，不必在每次提问时重复提供。`SOUL.md`、`USER.md` 和 `MEMORY.md` 也可能由 Dream 整理更新，后续可用 `/dream-log` 审阅长期资料的变化。

## 4. 提示词约束与强制限制

| 想达到的效果 | 实现位置 |
| --- | --- |
| 统一语气、分析步骤、引用格式 | `SOUL.md`、项目 `AGENTS.md`，再用实际回答验证遵循情况 |
| 校验日期、币种、指标口径与计算公式 | 自定义 Tool、MCP 服务或业务代码中的参数与计算校验 |
| 限制工作区文件访问 | `config.json` 的 `tools.restrictToWorkspace` 与会话访问模式；shell 的进程隔离需配合 `tools.exec.sandbox`，macOS 支持 `seatbelt` |
| 禁用 shell 执行能力 | `config.json` 的 `tools.exec.enable = false`；文件写入和其他工具能力需分别控制 |
| 确保不执行交易 | 不提供可执行交易的接口或凭据，或在业务服务中强制检查授权；同时用项目指令约定职责 |

system prompt 是模型决策的输入，无法单独保证每次都遵守规则。例如，“禁止下单”应同时对应交易能力的限制，而不只是一句文字。配置字段应合并进已有对象，不要替换整份 `config.json`；修改启动配置后按原方式重启 Gateway。工作区规则也不能放宽运行时或操作系统已经设置的权限。

## 5. 修改后何时生效与怎样检查

普通新回合组装上下文时会重新读取工作区 Markdown，因此手动编辑后无需再次 `onboard`，也通常无需为这几份文件重启 Gateway。正在执行的回合可能已经持有旧上下文，最清楚的验证方式是等其结束后，新建会话做一轮对照测试。已有会话下一回合也会读取新文件，但仍保留旧历史；修改角色不会清空旧对话或长期记忆。历史压缩后重新组装上下文时仍读取这些规则文件。

在仓库根目录、已激活 Python 环境的终端中，可先只检查本地组装结果：

```bash
export LGX_NANOBOT_HOME="$PWD/tutorials_lgx/.runtime"

# 使用当前内部 ContextBuilder 检查默认项目；不会调用公司 API
python - <<'PY'
import os
from pathlib import Path
from nanobot.agent.context import ContextBuilder

def main() -> None:
    workspace = Path(os.environ["LGX_NANOBOT_HOME"]) / "workspace"
    messages = ContextBuilder(workspace).build_messages([], "角色配置检查")
    print("第一条消息角色：", messages[0]["role"])
    for filename in ("AGENTS.md", "SOUL.md", "USER.md"):
        loaded = f"## {filename}\n" in messages[0]["content"]
        print(f"{filename}：{'已注入' if loaded else '未注入'}")


if __name__ == "__main__":
    main()
PY
```

预期第一条消息角色为 `system`。本机当前未定制模板的实际结果为 `SOUL.md` 已注入、`AGENTS.md` 与 `USER.md` 未注入。修改后对应文件应显示已注入；这个命令仅验证默认项目的 prompt 组装，不证明模型遵循了规则。需要核对某条具体规则时，可在本地检查 `messages[0]["content"]` 是否包含该文本，不要把完整私有提示或长期资料复制进共享教材。

接着在 WebUI 新建默认项目会话，用公开或合成的小样本提问，检查角色表述、引用和工具调用。例如“根据提供的两年营收计算增长率，注明公式与单位”；有数据时检查计算工具是否被调用，缺数据时检查是否明确指出缺失项。该步骤会调用公司 API，尚待用户实际实验验证。
