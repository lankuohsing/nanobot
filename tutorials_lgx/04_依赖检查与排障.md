# 04：可编辑安装与依赖冲突排查

学习目标：理解安装输出，确认包进入正确环境，区分“nanobot 安装成功”和“整个环境的依赖兼容”。本文依据当前 [pyproject.toml](../pyproject.toml) 与 2026-11-18 的本机安装元数据；安装主流程见 [第 02 章](./02_首次运行.md#1-准备源码环境)。

## 1. 安装时需要先逐个检查依赖吗

不需要。激活选定环境后，从仓库根目录执行 `python -m pip install -e .`，pip 会自动读取项目声明并安装依赖。`-e` 表示可编辑安装，后续导入使用当前仓库源码；项目安装包叫 `nanobot-ai`，Python 模块和命令入口叫 `nanobot`。

使用 `python -m pip` 可确保安装工具与当前解释器一致。复用已有环境时，安装后再用 `python -m pip check` 检查所有已安装包的依赖约束；新同事没有共享环境需求时，使用独立环境通常更省事。

| 输出或检查 | 说明什么 | 还需要确认什么 |
| --- | --- | --- |
| `Successfully installed ... nanobot-ai-0.4.1 ...` | 本次安装已完成 | 同环境其他软件的依赖是否仍兼容 |
| `sys.executable` 指向所选环境 | 当前用了哪个 Python | `pip` 是否通过这个 Python 调用 |
| `nanobot.__file__` 指向仓库源码 | 当前导入了哪份代码 | 在仓库内导入也可能来自当前目录，应结合 `pip show` 的可编辑路径判断 |
| `python -m nanobot --version` | 当前模块能执行版本命令 | 模型调用、工具和界面功能另行验证 |
| `No broken requirements found.` | 已安装包的元数据依赖约束兼容 | 不代表每个包的全部功能都经过运行测试 |

## 2. 原始冲突输出如何理解

学习过程中曾出现下面两条冲突；它们是历史案例，当前修复后的结果见本章末尾。

```text
mlflow 3.14.0 has requirement cryptography<49,>=43.0.0, but you have cryptography 50.0.2.
gradio 5.50.0 has requirement pillow<12.0,>=8.0, but you have pillow 13.0.0.
```

pip 的警告表示：这次安装虽然成功，但共享环境中的已有应用要求不同的依赖范围。MLflow 要求的 cryptography 上限小于当前版本，Gradio 要求的 Pillow 上限也小于当前版本；这是安装包之间的约束冲突，不能只凭 nanobot 能导入就判断环境正常。

nanobot 并不依赖 MLflow 或 Gradio，因此不存在“nanobot 需要的 MLflow/Gradio 版本”。它们是同一个环境中的独立应用，通过 cryptography、Pillow 等共享依赖发生冲突。

当前源码要求 `cryptography>=46.0.0`、`pillow>=13.0.0,<14.0.0`。旧 Gradio 的 `pillow<12` 与 nanobot 的要求没有交集，直接降级 Pillow 会破坏 nanobot 的声明约束。旧 MLflow 与 nanobot 的 cryptography 要求原本有 `>=46,<49` 的交集，但还需检查传递依赖；例如本机 pyOpenSSL 26.4.0 要求 `cryptography>=49,<51`，只降 cryptography 又会造成另一处冲突。

`--force-reinstall` 只是重新安装，`--no-deps` 会跳过依赖安装；它们都不会自动消除相互冲突的版本要求。应选择约束兼容的应用版本，或拆分环境。

## 3. 先确认环境与版本

从仓库根目录执行，先激活需要检查的环境。`py312` 为作者已有的 Conda 环境名，新同事使用自己的环境。

```bash
conda activate py312
python -c 'import sys; print(sys.executable)'
python -m pip show nanobot-ai
python -m pip check

# 仅在这些独立应用也已安装时查看；nanobot 不要求安装它们
python -m pip show mlflow gradio cryptography pillow pyOpenSSL
```

检查命令不调用大模型。不要为了检查安装结果而再次安装 MLflow 或 Gradio；缺少这些包并不妨碍学习 nanobot。

## 4. 处理冲突的两种方式

需要保留其他项目的既有应用版本时，为 nanobot 建立独立环境。下面是 Conda 示例，从仓库根目录执行；只有首次需要创建环境。

```bash
conda create -n nanobot_lgx python=3.12
conda activate nanobot_lgx
python -m pip install -e .
python -m pip check
```

需要在同一个环境内继续使用这些应用时，检查它们较新版本的依赖范围，再让 pip 一起解析相关包。下面命令只是这种情况的操作示例，需要访问依赖源；先看预览，再决定是否执行实际升级。它不是每个新同事都要运行的安装步骤。

```bash
# 在需要调整的共享环境中预览方案，不执行安装
python -m pip install --dry-run --upgrade -e . mlflow gradio

# 确定接受预览中的版本变化后，才执行升级
python -m pip install --upgrade -e . mlflow gradio
python -m pip check
```

版本组合以依赖解析结果为准。升级后应重启使用旧包的进程，并验证自己实际使用的 MLflow/Gradio 功能；如果仍有冲突，继续检查提示中的包及约束，或改用独立环境。
