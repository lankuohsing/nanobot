# 06：工作区文件与会话存储

工作区保存 Agent 的指令、身份、长期资料和任务设置；逐条问答保存在工作区外的 SQLite 会话数据库。CLI 与 WebUI 可以使用同一数据库，但 WebUI 侧栏只列出属于网页会话命名空间的对话。本章依据当前源码，版本基准见 [README](./README.md)。

## 1. workspace 下的文件做什么

下表对应当前学习实例的 `tutorials_lgx/.runtime/workspace/`；这些文件多数在初始化或启动时生成，有文件不代表已经写入本次问答。

| 文件 | 作用 |
| --- | --- |
| `AGENTS.md` | 项目指令：分析步骤、工作约定、回复要求等。默认项目就是 Agent 工作区；另选项目时读取该项目的 `AGENTS.md` |
| `SOUL.md` | Agent 的身份、语气和行为风格 |
| `USER.md` | 用户资料与稳定偏好，例如语言、技术背景 |
| `HEARTBEAT.md` | 周期巡检的任务清单；启用 heartbeat 时检查，默认只有标题和注释，无任务会跳过 |
| `memory/MEMORY.md` | 跨会话复用的长期事实、偏好与工作背景 |
| `memory/history.jsonl` | 对话压缩产生的摘要记录，为 Dream 整理长期记忆提供材料；不是逐条聊天原文 |
| `prompts/README.md` | 工作区提示覆盖文件的说明；按需创建的 `dream.md`、`evaluator.md` 才是相应功能的自定义指令 |
| `cron/jobs.json` | 定时任务的调度、执行与投递设置；当前包含框架的 Dream、heartbeat 任务 |
| `.nanobot/workspace-id` | Agent 工作区的稳定标识；这个工作区下多个 session 共用它，用于选择会话数据库目录 |

本次检查中，几个 Markdown 文件均与随包模板相同，`memory/history.jsonl` 为 0 字节。因此，当前工作区文件没有记录刚才的逐条问答。后续对话被压缩时可能产生摘要；Dream 再从摘要提炼长期资料，工具也可能按任务要求写文件。收到一条回复不代表长期记忆已更新。

`ContextBuilder` 会跳过内容未修改的默认 `AGENTS.md`、`USER.md` 和 `MEMORY.md`，减少无效上下文。这个工作区的 `AGENTS.md` 是 nanobot 运行指令，与仓库和学习目录中指导开发协作的 `AGENTS.md` 作用不同。另选项目不会替换 Agent 自身的 `SOUL.md`、`USER.md` 和长期记忆。

压缩何时触发、输入预算如何计算、压缩结果保存在哪里，以及温度和输出上限在哪里修改，见 [第 07 章](./07_上下文压缩与模型参数.md)。

## 2. 刚才的问答存在哪里

先分清三个层次：`.runtime/` 是 `--home` 指定的实例目录；`.runtime/workspace/` 是当前 Agent 工作区；session 是一次可持续多轮的对话。`workspace-id` 标识 Agent 工作区，`session key` 标识其中的一份对话。

| 标识或目录 | 当前对应什么 | 与对话的关系 |
| --- | --- | --- |
| home：`.runtime/` | 配置与运行数据的根目录 | 保存配置、会话数据库、日志等 |
| `workspace-id` | `.runtime/workspace/` 这个 Agent 工作区 | 一个工作区下可以保存多个 session |
| `session key` | `lgx:company-first`、`websocket:<chat-id>` 等 | 每个 key 选择一份独立的对话历史 |

`workspace-id` 首次分配时是随机生成的 32 个字符的十六进制字符串，写入工作区的 `.nanobot/workspace-id`；它不是目录路径的哈希。正常重启和新建会话会复用它。当前只有一个 Agent 工作区，因此只有一个 workspace-id；CLI 和网页两份会话分别用自己的 session key 保存在同一个数据库里。网页另选项目只改变该会话的项目上下文，Agent 工作区标识仍相同。

使用同一 `--home`、默认 Agent 工作区的学习实例时，数据库位置为：

```text
tutorials_lgx/.runtime/
├── workspace/
│   ├── .nanobot/workspace-id
│   └── memory/...
└── sessions/<workspace-id>/sessions.sqlite3
```

这里 `<workspace-id>` 用于选择数据库目录；数据库内部再按不同的 `session key` 区分对话。可以将两者理解为“对话组的标识”和“组内某份对话的标识”。

数据库的 `sessions` 表保存会话标识和元数据，`messages` 表保存模型会话消息；WebUI 另外使用 `history_*` 表保存输入、回复片段、状态等显示记录。这些是同一个数据库中的不同层，模型消息条数不一定等于页面上的气泡数。

2026-11-18 只读检查确认：网页会话 `websocket:<chat-id>` 已保存一条用户消息和一条助手回复，也有网页显示记录；`lgx:company-first` 中已找到“只回复：连接成功。”的测试输入及包含“连接成功”的回复。完整对话留在本地数据库，不复制到教程。

在按第 05 章准备好的 macOS 终端中，可用下面的只读命令查看：

```bash
# 默认 Agent 工作区；另设 --workspace 时需替换这里的 workspace 路径
LGX_WORKSPACE_ID="$(cat "$LGX_NANOBOT_HOME/workspace/.nanobot/workspace-id")"
LGX_SESSION_DB="$LGX_NANOBOT_HOME/sessions/$LGX_WORKSPACE_ID/sessions.sqlite3"

# 列出数据库里的所有会话，包括 CLI 会话
sqlite3 -readonly -header -column "$LGX_SESSION_DB" \
  'SELECT key, created_at, updated_at FROM sessions ORDER BY updated_at DESC;'

# 查看这次 CLI 会话的问答；网页会话可替换 WHERE 中的 key
sqlite3 -readonly -line "$LGX_SESSION_DB" \
  "SELECT position, json_extract(record, '$.role') AS role,
          json_extract(record, '$.content') AS content
   FROM messages WHERE session_key = 'lgx:company-first'
   ORDER BY position;"
```

第一条查询应看到 CLI 与网页会话；第二条按顺序显示模型会话消息，其中可能含运行上下文或工具内容。网页显示优先在 WebUI 中查看。数据库运行时还可能出现 `-wal`、`-shm` 文件，它们属于 SQLite 的正常工作文件；这里使用 `-readonly` 查询，不修改运行状态。

## 3. CLI 会保存吗，为什么网页侧栏没有它

`python -m nanobot ... agent --session lgx:company-first -m "..."` 是单次 CLI 请求：回复后 Python 调用结束，会话仍持久化。以后带相同的 home、Agent 工作区和 `--session` 可以继续使用这份历史；更换 session 名称开启另一份对话，长期记忆仍共享。重复执行连接测试会追加消息。

当前 WebUI 的 `/api/sessions` 列表明确只返回 `websocket:` 开头的会话。CLI 的 key 是 `lgx:company-first`，所以网页侧栏不显示它；这次检查也确认 CLI 会话已落库。网页新建的对话与这次 CLI 对话有各自的历史。若后续实验需要直接在网页里回看，就在 WebUI 中创建和继续该对话。
